### Database Schema
```sql
CREATE TABLE price_ticks (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    base VARCHAR(255),
    quote VARCHAR(255),
    exchange ENUM('BINANCE', 'COINBASE', 'KRAKEN', 'MOCK'),
    bid NUMERIC(19,8) NOT NULL,
    ask NUMERIC(19,8) NOT NULL,
    timestamp TIMESTAMP(6) WITH TIME ZONE NOT NULL
);
```

## Trade-offs & Decisions

### 1. Record → Class Conversion
**Trade-off**: Lost immutability  
**Gain**: JPA compatibility  
**Mitigation**: Factory method for validation

### 2. 5-Second Time Window
**Rationale**: Balance freshness vs. data availability  
**Benefit**: Avoids stale price aggregation

### 3. Save-then-Query Pattern
**Trade-off**: Slight performance overhead  
**Benefit**: Database as source of truth, enables historical queries

## Lessons Learned

### 1. JPA Requires Compromises
- Records are elegant but incompatible with JPA
- No-arg constructors and mutability are JPA requirements
- Factory methods can maintain validation semantics

### 2. Mock Repository Design
- Simple return values aren't enough
- Must simulate persistence behavior (saves tracked, queries filtered)
- State management in test setUp is crucial

### 3. Backward Compatibility
- Constructor signature changes break all tests
- Systematic updates with scripts (`sed`) save time
- Factory methods minimize ripple effects
